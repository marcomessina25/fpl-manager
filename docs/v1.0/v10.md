# V1.0 — Stable FPL Decision-Support Platform

> **Status:** **Completed (`v1.0.0`)** on 2026-09-22 (`version_10` branch)  
> **Canonical Quantitative Model Report:** [`reports/v10_canonical_model_report.md`](../../reports/v10_canonical_model_report.md)  
> **Frozen V0.9 Baseline:** [`reports/v09_frozen_baseline.json`](../../reports/v09_frozen_baseline.json)  
> **Performance Benchmarks:** [`reports/v10_performance_benchmarks.json`](../../reports/v10_performance_benchmarks.json)

>
> **Goal:** Make the existing FPL Manager feature set stable, reproducible, tested, measurable, and demonstrably useful.
>
> V1.0 is **not** intended to complete every possible research direction. It is the first release in which the complete decision-support loop can be trusted as a production baseline.

---

# 0. V1.0 philosophy

The V1.0 target is:

```text
Official FPL data
        ↓
Point-in-time snapshots
        ↓
Deterministic rules / state
        ↓
Quantitative projections
        ↓
Optimizers / planners
        ↓
Strategic risk & ownership
        ↓
Structured manager dossier
        ↓
Optional LLM qualitative analysis
        ↓
Deterministic validation
        ↓
Human decision
        ↓
Decision log
        ↓
Actual outcome
        ↓
Evaluation / backtesting
```

The release succeeds when this entire loop is stable and reproducible.

V1.0 should optimize for:

```text
Correctness
    >
Data quality
    >
Prediction quality
    >
Decision quality
    >
Evaluation
    >
UX
    >
Feature count
```

Research that does not improve the release baseline should remain outside the critical path.

# P1 — Data and model reproducibility

## Objective

Make every quantitative prediction traceable to its exact data and model configuration.

The existing roadmap requires point-in-time snapshots and explicit model metadata.

## 1.1 Point-in-time integrity

Verify every prediction uses only information available before the Gameweek deadline.

Permanent protections must cover:

- final GW statistics;
- future injury information;
- future price changes;
- future ownership;
- post-deadline team news;
- future fixtures/results;
- later versions of statistics.

### Tests

Create leakage tests that deliberately inject future information and verify that the point-in-time pipeline rejects or excludes it.

---

## 1.2 Model registry

Every prediction should expose:

```text
model_version
training_data_cutoff
feature_set_version
parameter_version
prediction_timestamp
```

Add a single canonical representation for this metadata.

### Acceptance

A historical prediction can be reconstructed from:

```text
snapshot
+
model metadata
+
configuration
```

without relying on undocumented local state.

---

## 1.3 Model report

Create a canonical quantitative-model report containing:

- xP MAE;
- xP RMSE;
- Spearman;
- bias;
- xM MAE;
- xM RMSE;
- availability metrics;
- calibration;
- position breakdown;
- price breakdown;
- minutes/error buckets;
- known limitations.

---

# P2 — Decision engine

## Objective

Make the decision engine explicit about the distinction between **prediction** and **decision objective**.

## 2.1 Neutral strategy

The neutral profile should use calibrated expected points directly.

Production principle:

```text
prediction
    ↓
calibrated xP
    ↓
legal lineup optimization
```

Do not apply a second hidden participation discount.

The V0.9 experiment established `lineup_penalty_weight = 0.0` as the V1.0 baseline.

---

## 2.2 Participation information

Participation modelling remains available to the decision layer through:

- P(start);
- P(sub);
- P(play);
- expected minutes;
- role/regime information;
- player availability.

Do not remove these signals merely because the explicit lineup penalty is zero.

Future risk-aware objectives may consume them directly.

---

## 2.3 Risk profiles

Verify and document:

```text
neutral
floor
ceiling
defend_lead
chase
```

For each profile define:

- mathematical objective;
- configurable parameters;
- expected behaviour;
- validation metrics;
- historical test result.

A profile must not be exposed as a meaningful strategy if its objective has not been validated.

---

## 2.4 Captaincy

Captaincy must remain separately validated.

Measure:

- captain points;
- captain regret;
- zero-minute captain rate;
- vice-captain fallback;
- captain risk;
- captaincy exposure.

Do not assume lineup risk controls automatically solve captaincy risk.

---

# P3 — Optimizers and multi-GW planning

## Objective

Turn the existing optimization infrastructure into a validated V1.0 decision layer.

## 3.1 Transfer optimizer

Verify:

- 1 transfer;
- 2 transfers;
- 3 transfers;
- 4 transfers;
- 5 transfers;
- budget;
- selling price;
- club limits;
- free transfers;
- hit costs;
- transfer chains.

### Correctness test

For small synthetic pools:

```text
branch-and-bound optimum
==
exhaustive optimum
```

Extend exhaustive-equivalence testing as far as computationally practical.

---

## 3.2 Wildcard / Free Hit

Verify:

- legality;
- budget;
- club limits;
- position constraints;
- bench;
- starting XI;
- objective calculation.

Document clearly that the current local-search implementation is heuristic unless an exact global solver is introduced.

---

## 3.3 Multi-GW planner

Validate the existing 3–6 GW planner.

It must correctly handle:

- roll decisions;
- free-transfer banking;
- transfers;
- transfer hits;
- projected points;
- fixture changes;
- chip interactions;
- weekly state transitions.

### Required comparison

For selected small synthetic problems, compare planner output with exhaustive enumeration where feasible.

---

## 3.4 Decision reproducibility

Given identical:

```text
snapshot
squad
configuration
model version
```

the optimizer should produce the same recommendation.

If stochastic algorithms are introduced, the seed/configuration must be recorded.

# P4 — LLM and provider layer

## Objective

Make LLM assistance useful without allowing it to become a source of numerical or legality errors.

The architecture remains:

```text
deterministic engine
        ↓
candidate strategies
        ↓
structured comparison
        ↓
LLM critique
        ↓
qualitative evidence
        ↓
deterministic validation
        ↓
human decision
```

## 4.1 Provider abstraction

Verify:

- common provider interface;
- provider configuration;
- timeout;
- malformed-response handling;
- authentication failures;
- rate-limit handling;
- unavailable-model handling.

---

## 4.2 Reliable external provider

At least one external provider must pass an end-to-end acceptance test:

```text
create key
   ↓
authenticate
   ↓
send exact application prompt
   ↓
receive response
   ↓
parse response
   ↓
handle errors
   ↓
run through GUI
   ↓
validate actions
```

The offline heuristic fallback must remain functional.

---

## 4.3 Deterministic guardrails

LLM output must never directly mutate:

- squad legality;
- budget;
- transfer state;
- captaincy state;
- chip state.

Every proposed action must pass deterministic validation.

---

## 4.4 LLM evaluation

Record:

- model/provider;
- prompt/context version;
- recommendation;
- deterministic validation result;
- human acceptance/rejection;
- eventual outcome.

Do not evaluate the LLM merely by whether its prose appears plausible.

---

# P5 — Evaluation and historical backtesting

## Objective

Make evaluation a permanent part of the application rather than a collection of one-off research scripts.

## 5.1 Prediction evaluation

Maintain:

- MAE;
- RMSE;
- bias;
- Spearman;
- calibration;
- xM metrics;
- availability metrics;
- position breakdown;
- price breakdown;

---

## 5.2 Decision evaluation

Measure:

- total points;
- net points;
- transfer gain;
- hit cost;
- bench regret;
- captaincy regret;
- zero-minute starters;
- zero-minute captains;
- transfer ROI;
- chip ROI.

Separate:

```text

captaincy error
transfer error
chip error
```

---

## 5.3 Human vs model

For every logged decision where both are available:

```text
model recommendation
human recommendation
final decision
actual outcome
```

Calculate:

- model score;
- human score;
- hybrid score;
- difference;
- regret;
- confidence.

Avoid interpreting a single season as proof of universal superiority.

---

## 5.4 Counterfactual evaluation

Clearly distinguish:

```text
observed outcome
```

from:

```text
hindsight counterfactual
```

For each historical Gameweek where the necessary data exists, record:

- actual decision;
- model decision;
- alternative legal decisions;
- hindsight best legal decision;
- resulting points.

---

## 5.5 Decision-weighted errors

Continue the V0.9 approach using:

- projected xP;
- squad-selection probability;
- captaincy probability;
- price;
- optimizer exposure;
- transfer relevance.

Document the weighting formula.

Do not introduce arbitrary weights without validation.

# P11 — V1.0 release gate

V1.0 should only become a release candidate when all of the following are true:

```text
CORRECT
  ↓
TESTED
  ↓
REPRODUCIBLE
  ↓
HISTORICALLY VALIDATED
  ↓
DOCUMENTED
  ↓
INTEGRATED
  ↓
PR-READY
```

### Release blockers

Any of the following blocks V1.0:

- known state corruption;
- illegal squad/transfer/lineup decisions;
- future leakage;
- irreproducible historical results;
- broken migration;
- uncontrolled LLM state mutation;
- secrets exposed in logs;
- failing critical regression tests;
- optimizer producing illegal output;
- undocumented model configuration affecting decisions.

# P13 — Definition of V1.0 success

V1.0 succeeds if the project can answer the following reproducibly:

### Before a Gameweek

> What does the model currently expect?

### For my squad

> What legal actions are available?

### For each action

> What is the expected value and strategic implication?

### With LLM assistance

> What qualitative factors deserve human attention?

### After the Gameweek

> What actually happened?

### During evaluation

> Was the prediction wrong, or was the decision wrong?

### Across history

> Does the system provide measurable value compared with meaningful baselines?

### For future development

> Which errors are important enough to justify changing the model?

---

# Final V1.0 principle

> **Do not make V1.0 the end of research. Make it the beginning of trustworthy experimentation.**

The release should establish a stable, reproducible baseline from which V1.1+ can make measured improvements without destabilizing the core system.
