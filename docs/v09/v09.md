# V0.9 — Predictive Model Improvement, Closed-Loop Evaluation & Production Hardening

> **Purpose:** Build directly on the V0.8 evidence and turn the current participation heuristic into a stronger, learned and calibrated predictive system, while simultaneously closing the loop between prediction quality and actual FPL decision quality.

---

# 1. Executive objective

V0.8 successfully attacked the weakness identified in V0.7: participation and expected minutes.

The latest 2025-26 validation shows materially better performance:

- xM MAE: **13.92 minutes**
- xP MAE: **1.150 points**
- Spearman: **0.6750**
- xM bias: approximately **-0.12 minutes**
- availability precision: **81.8%**
- availability recall: **83.7%**

However, the model is still weakest in the intermediate participation/rotation region.

Therefore the central V0.9 question is:

> **Can we turn the V0.8 participation heuristic into a learned, calibrated temporal model that improves both prediction quality and actual FPL decisions across multiple seasons?**

V0.9 should not be a generic feature-expansion release.

The development principle is:

```text
V0.8 baseline
     ↓
identify residual errors
     ↓
learn the participation structure
     ↓
calibrate probabilities
     ↓
validate out-of-sample
     ↓
integrate into xM/xP
     ↓
re-run identical decision simulations
     ↓
measure real decision benefit
```

# 2. V0.9 priorities

| Priority | Workstream | Weight | Goal |
|---|---|---:|---|
| P0 | V0.8 baseline freeze | 10% | Reproducible control |
| P1 | Participation error decomposition | 15% | Understand remaining failures |
| P2 | Learned P(start)/P(play) model | 20% | Replace hand-tuned weights |
| P3 | Conditional minutes model | 15% | Improve 0/30/60/90-minute separation |
| P4 | Probability calibration | 10% | Make probabilities meaningful |
| P5 | Rotation/regime modelling | 10% | Handle role changes and congestion |
| P6 | Decision-aware evaluation | 10% | Prove model value downstream |
| P7 | Broader xP calibration | 5% | Improve remaining xP components |
| P8 | Production hardening / observability | 5% | Make experiments and live operation robust |

These weights are priorities, not a requirement that development time be distributed mechanically.

---

# 3. What V0.8 established

V0.8 should become the new frozen control.

It demonstrated that the participation hypothesis was correct:

```text
V0.7
xM weak
rotation errors high
        ↓
V0.8
explicit participation modelling
        ↓
xM materially better
xP materially better
```

But the remaining error pattern is important.

The latest 2025-26 xM bucket results show approximately:

| Predicted xM | MAE |
|---|---:|
| 0–15 | 4.4 min |
| 16–30 | 26.5 min |
| 31–60 | **33.9 min** |
| 61–75 | 27.0 min |
| 76–90 | 15.0 min |

The central weakness is therefore not simply "minutes are inaccurate."

It is:

> **The model has difficulty identifying the intermediate states between non-playing, substitute appearance, rotation, and reliable starter.**

This should drive the V0.9 architecture.

---

# 4. V0.9 Phase 0 — Freeze the V0.8 control

Before changing the predictor:

- record the V0.8 commit;
- preserve the V0.7 predictor;
- preserve V0.8 configuration;
- preserve benchmark datasets;
- preserve report generation commands;
- record experiment metadata;
- ensure identical historical snapshots can be reused.

Every V0.9 result must be comparable against:

```text
V0.7
V0.8
V0.9 candidate
```

No experiment should silently replace the baseline.

# 5. Phase 1 — Build the residual-error dataset

V0.8 already has participation diagnostics. V0.9 should make them the central research dataset.

For each player/Gameweek capture:

```text
season
gameweek
player_id
team_id
position
price
FPL status
chance of playing
p_start
p_sub
p_play
expected_minutes
actual_minutes
actual_started
actual_points
```

and historical features available at the decision point.

Classify errors into:

```text
NO_APPEARANCE
BENCHED
SUB_APPEARANCE
EARLY_SUBSTITUTION
ROLE_LOSS
RETURN_FROM_INJURY
TACTICAL_CHANGE
CONGESTION
UNKNOWN
```

The classification must never use post-deadline information as an input to the prediction.

It may use the actual outcome for **diagnostic labelling**, because this is an evaluation dataset.

# 6. Phase 2 — Stop thinking of participation as one number

The V0.9 target should be a structured probability model.

Conceptually:

```text
                       Player / GW
                            │
              ┌─────────────┴─────────────┐
              ↓                           ↓
        P(no appearance)              P(appearance)
                                          │
                                  ┌───────┴───────┐
                                  ↓               ↓
                               P(start)        P(sub)
                                  │               │
                                  ↓               ↓
                         minutes | start   minutes | sub
                                  │               │
                                  └───────┬───────┘
                                          ↓
                                  expected minutes
                                          ↓
                                         xP
```

The exact mathematical structure can evolve during experimentation.

The important requirement is that the model explicitly represents the different participation states.

# 7. Phase 3 — Learn P(start)

## Objective

Estimate:

```text
P(start | information available before deadline)
```

### Candidate features

Use only information available at the decision point:

### Recent participation

- starts last 3;
- starts last 5;
- minutes last 3;
- minutes last 5;
- starts last 10;
- minutes last 10;
- consecutive zero-minute matches;
- recent start-rate trend.

### Historical role

- season start rate;
- season minutes;
- starts per appearance;
- historical rotation rate.

### Schedule

- days since previous match;
- matches in previous 7 days;
- matches in previous 14 days;
- days until next match;
- European fixture proximity;
- domestic cup proximity.

### Player/team context

- position;
- team;
- team rotation rate;
- position-specific team rotation;
- player-specific rotation pattern.

### Status

- FPL availability;
- chance of playing;
- injury/doubt indicators where available before deadline.

### Price/role priors

These may remain as features, but their contribution must be learned or validated rather than arbitrarily imposed.

---

# 8. Phase 4 — Train a baseline statistical model

Start simple.

Candidate models:

1. Logistic regression.
2. Gradient boosting.
3. Random forest / equivalent tree model.

Do not start with deep learning.

The first question is:

> Can a relatively small learned model beat the V0.8 heuristic?

The baseline should be reproducible and interpretable.

---

# 9. Phase 5 — Learn P(sub)

A player who does not start is not equivalent to a player who will not play.

Estimate:

```text
P(appearance | not starting)
```

Candidate features:

- historical substitute appearance rate;
- recent bench appearances;
- average substitution minute;
- position;
- team substitution patterns;
- player role;
- recent starts;
- recent minutes;
- manager/team behaviour.

This should reduce the current ambiguity between:

```text
0 minutes
```

and:

```text
10–30 minutes
```

---

# 10. Phase 6 — Conditional minutes model

Instead of predicting minutes directly, model:

```text
E[M | start]
E[M | substitute appearance]
```

The V0.8 architecture already points toward this formulation.

V0.9 should learn these distributions from historical observations.

For starters, consider:

```text
minutes_if_start
```

as a distribution rather than a single hard-coded value.

For substitutes:

```text
minutes_if_sub
```

should similarly be estimated from comparable historical appearances.

---

# 11. Phase 7 — Consider categorical minute modelling

The strongest candidate experiment for the current error profile is to test whether minutes are better represented as states.

For example:

```text
0
1–29
30–59
60–74
75–90
```

or a similar discretisation.

Compare:

```text
continuous regression
vs
categorical model
vs
two-stage probability × conditional regression
```

Do not assume one is superior.

Select based on out-of-sample results.

---

# 12. Phase 8 — Probability calibration

A probability is useful only if it is calibrated.

If the model predicts:

```text
P(start) = 0.80
```

then comparable groups should start approximately 80% of the time.

Measure:

- Brier score;
- log loss;
- reliability diagrams;
- calibration curves;
- calibration by position;
- calibration by probability bucket;
- calibration by role cohort.

Candidate calibration methods:

- Platt scaling;
- isotonic regression;
- beta calibration.

Only retain a calibration method if it improves out-of-sample calibration without damaging ranking quality.

---

# 13. Phase 9 — Temporal training discipline

FPL is a time-series decision environment.

Random train/test splits should not be the primary evaluation methodology.

Prefer:

```text
Train:
    earlier Gameweeks/seasons

Validate:
    later Gameweeks

Test:
    completely unseen Gameweeks/seasons
```

Use rolling-origin evaluation where practical.

Example:

```text
Train GW1–10
Test GW11

Train GW1–11
Test GW12

...
```

The final test period must remain untouched during feature/model selection.

---

# 14. Phase 10 — Rotation regime detection

One of the major weaknesses in the current model is that historical information can remain stale after a player's role changes.

V0.9 should explicitly detect regime changes.

Examples:

```text
nailed starter
     ↓
rotation

rotation
     ↓
starter

starter
     ↓
injury

injury
     ↓
starter
```

Useful signals:

- consecutive benchings;
- abrupt minutes changes;
- abrupt start-rate changes;
- manager change;
- transfer to another club;
- formation/position change;
- team tactical change.

Recent evidence should be weighted more heavily when a regime transition is detected.

---

# 15. Phase 11 — Player-specific rotation fingerprints

Measure each player's historical response to:

- normal rest;
- short turnaround;
- European fixture;
- cup fixture;
- dense fixture periods.

Potential derived statistics:

```text
P(start | normal rest)
P(start | short rest)
P(start | Europe before)
P(start | Europe after)
P(start | 2+ matches in 7d)
```

Use smoothing/shrinkage so players with little data do not generate extreme probabilities.

---

# 16. Phase 12 — Manager/team rotation behaviour

Model the team environment.

Examples:

```text
team_rotation_rate
team_position_rotation_rate
manager_rotation_rate
player_rotation_vs_team_rotation
```

A player who starts 70% of matches for a team rotating heavily may be very different from one starting 70% for a team with almost no rotation.

Manager changes should create a new modelling regime where possible.

---

# 17. Phase 13 — Injury and availability modelling

The V0.8 model demonstrated a major improvement over the previous binary availability handling.

V0.9 should investigate:

```text
FPL status
+
chance of playing
+
recent minutes
+
recent starts
+
external information
```

rather than treating one status field as ground truth.

Where external football information is available, keep the information provenance explicit:

```text
FACT
INFERENCE
RUMOUR
MODEL_ASSUMPTION
```

External information must remain separate from the underlying historical statistical data.

---

# 18. Phase 14 — xM acceptance testing

The new model must be compared against V0.8 using:

### Global metrics

- MAE;
- RMSE;
- bias.

### Distribution metrics

- error by predicted-minute bucket;
- error by actual-minute bucket;
- zero-minute false positives;
- unexpected starts;
- unexpected bench appearances.

### Probability metrics

- Brier score;
- log loss;
- calibration.

### Decision metrics

- selected-player zero-minute rate;
- bench regret;
- captain zero-minute rate;
- points lost through minutes errors.

The central question is:

> **Does the new model fix the errors that actually matter for FPL decisions?**

---

# 19. Phase 15 — Decision-weighted model evaluation

Aggregate MAE can hide important failures.

For example:

```text
£4.5m bench player:
    40 → 0 minutes

£12.0m premium captain candidate:
    40 → 0 minutes
```

Both are 40-minute errors.

They are not equally important.

V0.9 should therefore calculate decision-weighted error using:

- projected xP;
- squad selection probability;
- captaincy probability;
- price;
- optimizer exposure;
- transfer relevance.

The exact weighting must be documented and tested rather than arbitrarily chosen.

---

# 20. Phase 16 — xP component calibration

Once participation is improved, return to the components of xP.

Potential areas:

- xG conversion;
- xA conversion;
- non-penalty xG;
- penalty probability;
- clean sheets;
- goals conceded;
- bonus;
- cards;
- defensive contribution.

The existing roadmap explicitly defers broader xP component calibration to V0.9.

The rule remains:

> **Only retain a feature or calibration if it demonstrates incremental out-of-sample value.**

Do not optimise coefficients against the final test season.

---

# 21. Phase 17 — Investigate the optimizer

V0.9 must separate two questions:

### Prediction quality

```text
Is V0.9 a better predictor?
```

### Decision quality

```text
Does the optimizer exploit the better prediction?
```

The latest 2025-26 full-season replay demonstrates why this distinction matters.

A better prediction model does not automatically guarantee that every optimizer configuration beats every simpler strategy.

Therefore compare:

```text
Simple xP
V0.8 Optimizer
V0.9 Optimizer
No Transfer
```

under identical starting conditions.

---

# 22. Phase 18 — Transfer ROI

For every transfer strategy measure:

```text
gross gain
hit cost
net gain
1-GW ROI
3-GW ROI
5-GW ROI
```

Separate the effects of:

```text
transfer
captaincy
lineup
chip
```

This helps determine whether a transfer model is actually creating value or simply moving points between decision categories.

---

# 23. Phase 19 — Model vs human closed loop

Use the existing decision-log architecture to compare:

```text
Model recommendation
Human recommendation
Final decision
```

Record:

- projected xP;
- alternative strategies;
- actual points;
- rank impact;
- decision confidence.

Over time compare:

```text
Model
Human
Hybrid
```

The purpose is not to prove that the model always wins.

The purpose is to determine:

> **Where does the human add information that the model lacks, and where does the model outperform human intuition?**

---

# 24. Phase 20 — Counterfactual analysis

For each Gameweek:

```text
What did the model recommend?
What did the human choose?
What would each have scored?
What was the best legal hindsight decision?
```

The final item must be explicitly labelled:

> **Hindsight only.**

Never use hindsight information to construct a supposedly pre-deadline prediction.

---

# 25. Phase 21 — LLM role

The LLM remains a qualitative analyst.

Preferred architecture:

```text
Deterministic prediction
        ↓
Optimizer
        ↓
5–20 candidate strategies
        ↓
Structured dossier
        ↓
LLM critique
        ↓
Evidence/context
        ↓
Deterministic re-validation
        ↓
Human
```

The LLM may identify:

- injury uncertainty;
- rotation risk;
- tactical changes;
- set pieces;
- fixture-specific risks;
- hidden assumptions.

It must not:

- bypass legality;
- directly mutate squad state;
- replace numerical optimization;
- be treated as a source of truth.

---

# 26. Phase 22 — Provider abstraction

The existing roadmap places provider expansion later, but V0.9 should ensure the abstraction exists even if only one external provider is used.

The provider interface should isolate:

```text
provider
model
credentials
request
response
error
rate limit
timeout
```

The application must remain functional through the offline heuristic fallback.

Provider expansion itself can remain a later V1.1 research track.

# 27. Phase 23 — Production hardening

V0.9 should implement the engineering items already present in the roadmap:

- configuration abstraction;
- provider interface;
- typed API models;
- structured errors;
- improved logging;
- transaction-like state updates;
- concurrency handling;
- migration tests;
- reproducible environment;
- CI;
- linting;
- type checks;
- regression fixtures.

The aim is not cosmetic cleanup.

The aim is to make model experiments and live decision workflows safe and reproducible.

# 28. Phase 24 — Security

Maintain the V0.6/V0.65 security principles:

- local-only default where appropriate;
- explicit bind address;
- safe CORS;
- secret redaction;
- no API-key persistence;
- no API-key logging;
- provider-specific secret handling;
- documented trust boundaries.

LLM functionality must always be optional.

The FPL engine must remain usable without an external LLM provider.

# 30. Multi-season requirement

No major V0.9 model should be accepted because it performs better on one season alone.

The historical framework already contains:

- 2021-22
- 2022-23
- 2023-24
- 2024-25
- 2025-26

Use multiple seasons to test robustness.

A candidate that improves 2025-26 but degrades the other seasons should be investigated, not automatically accepted.

---

# 31. Avoid overfitting to the 2025-26 report

The latest 2025-26 result is encouraging, but it must not become the training target.

Use the current results to identify hypotheses.

Do not tune the model until:

```text
2025-26 looks best
```

Instead:

```text
Hypothesis
 ↓
training period
 ↓
validation
 ↓
locked test
 ↓
cross-season confirmation
```

# 33. Definition of Done

## Prediction

- [ ] V0.9 participation model beats V0.8 out-of-sample or provides a clearly demonstrated calibration/decision advantage.
- [ ] P(start) is calibrated.
- [ ] P(play) is calibrated.
- [ ] Conditional minutes are validated.
- [ ] Rotation cohort errors improve.
- [ ] No leakage is detected.
- [ ] Multi-season robustness is demonstrated.

## Decision quality

- [ ] Better prediction produces measurable downstream benefit.
- [ ] Optimizer results are reproducible.
- [ ] Simple xP and optimizer baselines remain available.
- [ ] Transfer ROI is measured.
- [ ] Regret is measured.
- [ ] Model/human divergence is measurable.

## Software

- [ ] Tests pass.
- [ ] CI is reliable.
- [ ] State updates are safe.
- [ ] Errors are structured.
- [ ] Provider failures cannot corrupt squad state.
- [ ] Secrets are not persisted or logged.

## Research

- [ ] Every accepted model change has an experiment record.
- [ ] Failed experiments are documented.
- [ ] Test periods are not used for tuning.
- [ ] Results identify season and model versions.
- [ ] Known limitations are documented.

# 36. Strategic decision gate for V0.9 → V1.0

At the end of V0.9, every major component receives one of four dispositions:

```text
KEEP
```

if it consistently improves out-of-sample performance.

```text
CALIBRATE
```

if the concept works but needs refinement.

```text
REDESIGN
```

if systematic errors remain.

```text
REMOVE
```

if complexity does not create measurable value.

The V1.0 scope should then be built from these results rather than from a fixed feature checklist.

# 37. The central V0.9 experiment

If only one research question is answered in V0.9, it should be:

> **Can a learned and calibrated participation model recover the points currently lost because the system incorrectly expects a player to start or play meaningful minutes?**

The clean experiment is:

```text
Frozen V0.8
      │
      ├── predictor
      ↓
    optimizer
      ↓
 historical replay
      │
      │
      └───────────────┐
                      │
Candidate V0.9       │
participation model  │
      ↓              │
same optimizer       │
      ↓              │
same replay          │
      └──────────────┘
             ↓
       compare outcomes
```

The acceptance criterion is not simply:

```text
lower xM MAE
```

It is:

```text
lower xM error
+
better calibration
+
fewer costly participation mistakes
+
better downstream decisions
```

# 38. Final strategic direction

The project should now evolve as:

```text
V0.7
Measurement
    ↓
V0.8
First evidence-driven participation improvement
    ↓
V0.9
Learn + calibrate + close the decision loop
    ↓
V1.0
Stable, reproducible, useful FPL decision-support platform
    ↓
V1.1
Multi-provider / extended LLM research
```

The most important principle remains:

> **Do not add complexity because the model feels imperfect. Add complexity when the historical evidence identifies a specific failure that the complexity can plausibly fix.**

V0.8 has already provided that evidence.

The next release should therefore make the participation model **learned, calibrated, temporally robust, and decision-aware**, while preserving the deterministic optimizer and legality layers that already form the foundation of the system.
